# Agent Note: 0.2.0-rc.2 适配(四处契约漂移: 图标命名 / settings 模型 / Typert strict codec / bash terminal card)

> Status: verified — 单测 315 pass / 0 fail、client-selfcheck 通过、真机 GUI 端到端验证(连接主机 / 打开远程工作区 / 执行 bash / 读写文件 / **点击展开 bash 命令与输出**均正常, 2026-10-10)
> 范围: 本仓库 packages/dsh-ssh 在 DSH 0.2.0-rc.2 + pnpm 11.24 + node 22 上的安装与运行时验证。
> 前次同类记录见 research/2026-08-29-0.1.1-rc.2-adaptation.md(那次结论是"seam API 未漂移, 只需改 peer 版本"); 本次相反 —— 有 4 处实质契约变更, 其中第 4 处由用户实操发现。

## Problem

把 dsh-ssh 从 0.1.1-rc.2/0.1.2 升到 0.2.0-rc.2 时, 装上是装上了, 但运行时连爆四个错, 分别落在客户端渲染、设置持久化、远程 RPC、bash 卡片交互四条不同路径上。表面像四个独立 bug, 实际是 0.2.0-rc.2 的四处契约演进。

## Decision

### 1. 客户端图标: 按"笔画粗细"改名, 不再按像素尺寸

0.1.2 的图标名带尺寸后缀(`IconPlusOutline16` / `IconChevronDownOutline14` / `IconInspectOutline12`), 0.2.0-rc.2 全部改为 `<Name>Regular` / `<Name>Medium`。经核对, **12 个旧名字在新包中occurrences=0**(完全不存在), 不是别名保留。

语义变化: 旧名编码**尺寸**, 新名编码**笔画粗细**(`Regular`=1px, `Medium`=1.3px), 而每张 artwork 自带默认尺寸
(dsh-client-ui-primitives/lib/index.js:389 `IconPlusOutlineArtwork = ({ size = 16 })`, :482 ChevronDown `size = 14`)。

- 映射规则: 旧名 → `Regular` 变体(视觉等价, 同为 1px 笔画)。
- 调用点显式写的 `size: 14` 等仍然有效(`IconProps.size` 为可选 prop, 默认取 glyph 自带值), 所以 25 个调用点只改名、不改尺寸参数。
- 影响面: 设置页、bash toolview、两个 directoryFlow 槽全部会在渲染时抛 `React.createElement(undefined)`, 即整块 UI 失效。

### 2. settings: 运行时命名空间注册模型被移除, 改为插件自带 Config

| | ≤0.1.2 | 0.2.0-rc.2 |
|---|---|---|
| 声明 | `ctx.settings.register(ns, schema, {base, applies})` | `static Config = z.object({...})` + 字段 `.volatile()` |
| 读取 | `ctx.settings.get(ns)` | 构造函数第二参 `config`, 经 `config.field.get()` |
| 写入 | `ctx.settings.mutate(ns, ops, revision)` | `configEditor.edit(entry, (current, inherited) => next)` |
| 命名空间 | 插件自造字符串 | profile patch 行的 `id` |
| 持久化位置 | `~/.dsh/settings.yaml` | 活动 profile 的 `cordis.patch.yml` 行 `config:` |

关键事实(逐条已在 0.2.0-rc.2 源码核对):

- `ctx.settings.register` 与 `ctx.settings.get` **均已不存在**; `SettingsForms` 只暴露 `configure / writable / documentPath / prepareDocument / describe / update / replace / mutate`(dsh-settings/lib/index.js:322-544)。**没有跨命名空间读取的替代 API** —— 配置只能由拥有它的插件自己读。
- volatile 的语义: `.volatile()` 是纯元数据(schemastery 3.18.4 index.mjs:235-238), 但它决定两件事 —— ①**只有含 volatile 字段的 entry 才会生成设置表单**(dsh-settings:418-419 `volatileForm` 为空则整条 entry 被丢弃); ②volatile-only 变更走"就地更新 ref"路径而非重挂载, 所以 `this.config.x.get()` 在用户改设置后**立即返回新值, 无需重载**(cordis-plugin-loader:393-425 `_commitVolatile` → cosmokit:149-151 把新快照写回同一个 frozen ref)。
- 约束: volatile 字段必须位于**固定对象路径**上, 不能嵌在另一个 volatile 之下、数组元素里或 `sKey` 中(schemastery:241-252 `validateVolatileSchema`)。因此本插件的 `hosts` 整块 dict 标 volatile, 而非每个 host 条目单独标 —— dict 的 key 不是固定路径。
- 无 configEditor 时(dsh-settings 由 `!ctx.get('profileContext')` 门控)写入**不落盘**。本插件选择**显式报错**而非静默假装成功: `writeHosts` 在 `configWriter` 为空时抛"当前部署没有配置编辑器(configEditor), 主机配置无法持久化", 并让 `listHosts().writable=false`。
- 写路径做成**原子读改写**: `writeHosts(mutate, verb)` 在串行链内重新读取当前 hosts 再合并, 使并发保存互相叠加而非互相覆盖(每次 `edit` 都会覆盖行 `config.hosts` 整块)。`persisted:false` 表示这次是 no-op(值未变或条目不存在), 不是失败。

**遗留配置迁移**: dsh-settings 的 `importLegacyDocument`(:343-363)把旧的 `settings.yaml` 按顶层 section 名导入到**同名 entry id** 的 profile 行; `LEGACY_SECTION_ENTRIES`(:302-308)只重映射了 3 个官方 section。因此本插件把 profile patch 行的 id 定为 `dsh-ssh-hosts`(= 旧命名空间名), 让老用户已配的主机自动迁移。**该 id 是兼容性契约, 不可随意改名** —— 改名会让迁移静默失败(仅打 warn, 数据留在 `settings.yaml.imported`)。注意: 导入发生在 Loader 稳定后且只执行一次(文件先被 rename), 失败即不可重试。

反向的代价: 旧的 `dssh-hosts → dsh-ssh-hosts` 运行时读回退**已不可能实现**(没有跨命名空间读 API), 该迁移窗口就此关闭; 已在 0.1.x 使用且从未写入新命名空间的用户需手工迁移。这是模型变更带来的既成事实, 非本插件可绕开。

### 3. Typert strict codec: 内联 schema → create() 工厂

客户端 `$mount` 的 strict codec 从 `{ mode:'strict', typeSymbol, schema:{parse} }` 改为
`{ mode:'strict', typeSymbol, create: () => TypertSchema }`, 其中 `TypertSchema = { parse(value) }`
(dsh-typert-protocol/lib/types/types.d.ts:190-203)。校验点 dsh-typert-registry/lib/index.js:562-566
与 client.js:1355-1358 均要求 `typeof codec.create === 'function'`, 报错文案即用户所见
`strict codec has no create() factory`。官方生成描述符的 factory 会惰性实例化并缓存
(`typert.remote-client.js`: `() => (v ??= z.string())`), 本插件同样缓存单个透传 schema 实例。

注意 host 侧用 `src-json` codec, `validateCodec` 对 mode==='src-json' 直接放行, 不受此变更影响 —— 只有客户端那份 strict 描述符需要改。

### 4. bash toolview: terminal card 模型改为"解析参数"而非"读投影"

首次适配时**漏掉了这一处**, 由用户实操发现: bash 卡片能执行、但**点击无法展开**查看命令与输出, 而 write/edit 的 diff 可以点开。

0.2.0-rc.2 重写了官方的 `terminalCardModel`(dsh-client-ui-tool/lib/client.js:929-...):

| | ≤0.1.2 | 0.2.0-rc.2 |
|---|---|---|
| 数据来源 | `block.callView` / `block.resultView`(工具 `presentCall`/`presentResult` 的投影) | `parsedToolCall(block)` 解析 `call.argsRaw` + `singleResultText(block)` |
| 判定 | 投影上的 `card === 'terminal'` | `shellCall(name, args)`: 工具名必须是 `bash`/`pwsh` 且参数形状合法 |
| 退出码 | 投影自带 `exitCode`/`signal` | 客户端本地解析结果文本里的退出码标记 |
| 展开状态 | 组件内 `useState` | slot owner 注入的 **`useDisclosure`** prop |

**故障链**: `callView`/`resultView` 已不再产生 → 我们的 `sshTerminalCardModel` 恒返回 `null` → `expandable = false` → `root` 上不挂 `onClick` → 点击无反应。

**为什么只有 bash 受影响**: write/edit 走 `card:'read'`/文件变更另一条渲染路径, 且官方 file-mutation row 未被本插件覆写。

**附带发现**: 官方现在通过 `renderSlot(..., owner, ...)` 注入 owner props
`{ callId, toolName, ...call(含 phase/block), openFile, cwd, home, loadImage, useDisclosure, inspect }`
(dsh-client-ui-tool/lib/client.js:1832-1852), 并多一个 `phase === 'preparing'` 分支。occupant 必须接收 `useDisclosure` 与 `phase`, 否则无法参与宿主的会话级披露管理。

**修复**: 新增 `sshParsedToolCall`/`sshShellCall`/`sshValidEscalationFields`/`sshSingleResultText`/`sshParseExitStatusLocal` 对齐新解析方式; 接收并优先使用 `useDisclosure`(缺失时回退本地 state); 补 `preparing` 分支。保持本插件唯一差异: 仅将 terminal card 的最终 cwd 字符串由占位路径解码为可读远端路径。

### 5. 顺带发现: 配置文件读取曾被 PowerShell 编码破坏

用 `Get-Content -Raw` + `WriteAllText` 改写含中文/emoji 的源文件会把文件变成乱码(非 UTF-8 round-trip)。本轮 `client.js` 一度被毁, 已从 git 恢复。**改这类文件一律用 edit 工具或 node 的 `fs.readFileSync/writeFileSync`**, 不用 PowerShell 文本管道。

## Alternatives

- **图标**: 保留旧名并在 client.js 内做映射表 → 不采纳。旧名在新包中完全不存在, 映射表纯属自造兼容层, 且 `Regular` 已是等价的官方名称。
- **settings**: 用 `describe()` 读回自己的值代替 `config.x.get()` → 不采纳。`describe()` 对远程调用方强制脱敏(`redactSecrets:true`), 拿不到口令, 且多一次快照跳转; 自有 config 的 ref 才是权威来源。
- **settings**: 保留 `dssh-hosts` 双命名空间读回退 → 不采纳(技术上不可行, 见上)。
- **strict codec**: 继续内联 schema 并寄望运行时容忍 → 不采纳, 挂载期直接抛错, UI 整块不可用。
- **bash toolview**: 干脆不再覆写官方 bash row, 放弃 cwd 占位路径解码 → 不采纳。占位路径是远端工作区的实现细节, 直接显示给用户会暴露 `~/.dsh/remote/<hostId>/<base64>` 这种无意义字符串; 保留覆写但让差异收敛到"仅解码 cwd 一处"。

## Consequences(已验证事实)

- 单测基线 **315 pass / 0 fail**(较适配前 227 个用例净增, 含为各坑补的回归测试)。
- `scripts/client-selfcheck.mjs` 现在会**从已安装的 DSH 解析 primitives 的真实导出列表**(282 个)并逐个校验 client.js 引用的名字; 找不到 DSH 时打印 WARNING 降级而不是假装通过。已实测: 把任一带尺寸后缀的图标名塞回 client.js, 自检**必然失败**(`reads primitives the installed DSH does not export: IconPlusOutline16`)。
- `client-selfcheck.mjs` 还会**真实渲染注册的 bash occupant**(用 0.2.0-rc.2 形状的 result block), 断言 `data-expandable === true`、点击后 `aria-expanded === true`、展开内容含命令输出, 并确认后台调用不可展开。已实测: 把 `sshTerminalCardModel` 还原成旧的 callView/resultView 版本, 自检**必然失败**(`a settled bash call must be expandable (else clicking it does nothing)`)。
- `scripts/verify-typert-codec.mjs` 在真实组合中校验 host/client 两份描述符形状与 strict codec 契约, 输出 VERIFY-TYPERT-OK。
- `scripts/verify-settings-0.2.mjs` 校验插件服务在真实组合中装配并给出 wire 形状; 因 dsh-base 把 settings/config-editor 门控在 `profileContext` 上, 裸 boot 下该服务不激活, 脚本会明确 SKIP 设置表单断言而不是误报成功。
- 真机端到端(用户实操确认): 连接主机、打开远程工作区、执行 bash、读写文件、点击展开 bash 命令与输出全部正常。
- CI 增加一条纯数据 typert 形状自检(不需要 DSH 运行时), 守护 `create()` 这类挂载期契约。

## 待验证 / 已知缺口

- 设置表单在真实 GUI 中的**目视**确认(表单渲染样式、字段顺序)未做 —— 脚本受 `profileContext` 门控限制无法断言表单, 端到端只验证到"连接/浏览/执行/读写/展开"这一层。标**待验证**。
- 旧 `dssh-hosts` 命名空间的历史数据迁移: 新模型下只能依赖 `importLegacyDocument` 按 entry id `dsh-ssh-hosts` 自动导入; 若 `settings.yaml` 里存的是更早的 `dssh-hosts` section, 则**不会**被自动迁移(需手工处理)。标**待验证**, 取决于是否存在此类用户。
- 其余工具行(read/glob/grep/read_image)在 0.2.0-rc.2 下的展开行为**未逐一实操确认**: 它们的 toolview 未被本插件覆写(走官方路径), 理论上不受本处漂移影响, 但未见用户反馈也不等于已验证。标**待验证**。
